# Disaster Recovery — Architecture

This document describes the architecture of the Forage disaster recovery module as implemented on the `feature/disaster-recovery` branch.

## Module Structure

```
library/disaster-recovery/
├── pom.xml                          # Aggregator
├── forage-dr-core/                  # Storage SPI, exchange serialization, config
├── forage-dr-engine/                # Camel SPI hooks (the drop-in entry point)
└── forage-dr-store-jdbc/            # JDBC backend (Redis/Infinispan deferred)
```

| Module | Files | Role |
|---|---|---|
| `forage-dr-core` | 7 Java files | SPI contracts, snapshot model, config, serialization |
| `forage-dr-store-jdbc` | 4 Java + 1 SQL + 1 service | JDBC storage backend with TTL-based cleanup |
| `forage-dr-engine` | 8 Java + 1 service | Orchestration, route policies, intercept, replay |

## Dependency Flow

```
forage-dr-engine ──depends on──> forage-dr-core
forage-dr-engine ──depends on──> forage-dr-store-jdbc  (accepted coupling, decoupled later)
forage-dr-store-jdbc ──depends on──> forage-dr-core
```

Storage backends depend on `forage-dr-core` only, not on the engine. This mirrors how `forage-core-jdbc` is independent from `forage-jdbc`.

## Key Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Activation model | Zero-config | Same as `camel-observability-services` — add JAR, everything activates |
| Snapshot identity | Auto-generated BIGINT PK | Exchange IDs are random per-pod and meaningless across restarts |
| Snapshot cleanup | TTL-based expiry, purge-on-load | Same pattern as Camel IdempotentRepository with Redis/Infinispan |
| Replay semantics | At-least-once | Replayed exchanges re-execute external calls; dedup via IdempotentConsumer |
| Initialization | Deferred to CamelContextStartedEvent | Ensures DataSource and other beans are already in the registry |
| Observability | Independent from `camel-observability-services` | No cross-dependency; DR logs via SLF4J |
| Append-only snapshots | No upsert, no delete API | Expired rows purged on load; re-checkpointed replays create new rows |

## Class-by-Class Architecture

### forage-dr-core

#### `RecoveryStore` (interface)

Storage SPI — the contract any backend (JDBC, Redis, Infinispan) must implement.

```java
void saveCheckpoint(ExchangeSnapshot snapshot);
List<ExchangeSnapshot> loadCheckpoints(String routeId);
void saveShutdownExchange(ExchangeSnapshot snapshot);
List<ExchangeSnapshot> loadShutdownExchanges();
```

No delete methods. Snapshots expire via TTL and are purged on load.

#### `RecoveryStoreProvider` (interface)

Extends `BeanProvider<RecoveryStore>`. Discovered via ServiceLoader. The store is the *thing*, the provider is the *factory that creates it*. Standard Forage pattern (like `ModelProvider`, `DataSourceProvider`).

#### `SnapshotType` (enum)

Two values: `CHECKPOINT` and `SHUTDOWN`. Determines how a snapshot was created and which table it lands in.

#### `ExchangeSnapshot` (POJO)

Serializable representation of a Camel Exchange at a point in time.

| Field | Type | Notes |
|-------|------|-------|
| `id` | `long` | Auto-generated by the store (BIGINT), not exchange ID |
| `exchangeId` | `String` | Kept for logging/debugging only, not used as PK |
| `routeId` | `String` | Route the exchange belongs to |
| `body` | `byte[]` | Serialized exchange body |
| `headers` | `Map<String, byte[]>` | Serialized headers |
| `properties` | `Map<String, byte[]>` | Serialized exchange properties |
| `snapshotType` | `SnapshotType` | CHECKPOINT or SHUTDOWN |
| `timestamp` | `long` | Epoch millis when snapshot was taken |
| `partial` | `boolean` | True if some fields could not be serialized |

#### `ExchangeSnapshotSerializer` (utility)

Converts between live Camel `Exchange` and `ExchangeSnapshot`. Handles non-serializable objects gracefully (skips with warnings, marks snapshot as `partial`). Two static methods:

- `toSnapshot(Exchange, SnapshotType)` — serializes body/headers/properties via `ObjectOutputStream`
- `toExchange(ExchangeSnapshot, CamelContext)` — reconstructs via `DefaultExchange` and `ObjectInputStream`

#### `RecoveryConfigEntries` + `RecoveryConfig`

Standard Forage two-class config pattern. 9 configuration properties:

| Property | Default | Description |
|----------|---------|-------------|
| `forage.dr.enabled` | `true` | Master switch |
| `forage.dr.storage.backend` | `jdbc` | Storage backend |
| `forage.dr.checkpoint.enabled` | `true` | Enable checkpoint/resume |
| `forage.dr.shutdown.persistence` | `true` | Enable shutdown drain |
| `forage.dr.replay.on.startup` | `true` | Replay on restart |
| `forage.dr.ai.state.check.enabled` | `true` | Warn about in-memory AI providers |
| `forage.dr.snapshot.ttl.seconds` | `86400` | Snapshot TTL (default 24h) |
| `forage.dr.schema.auto.create` | `true` | Auto-create DB schema |
| `forage.dr.jdbc.datasource.name` | `dataSource` | Registry name of DataSource |

### forage-dr-store-jdbc

#### `JdbcRecoveryStore`

Implements `RecoveryStore` using plain JDBC. Constructor takes `DataSource` and `long ttlSeconds`.

- Two tables: `forage_dr_checkpoint` and `forage_dr_shutdown_exchange`
- PK is `id BIGINT AUTO_INCREMENT` (not exchange ID)
- Purge-on-load: each `load*` method calls `purgeExpired()` which deletes rows where `created_at <= cutoffTimestamp()`
- Maps serialized as single BLOB via `ObjectOutputStream`
- Errors logged, not thrown

#### `SchemaInitializer` (utility)

`initialize(DataSource)` creates both tables with `CREATE TABLE IF NOT EXISTS`. Indexes on `route_id` and `created_at`.

#### `JdbcRecoveryStoreProvider`

`@ForageBean(value="jdbc-recovery-store")`. Has `setDataSource(DataSource)` for wiring. `create()` runs `SchemaInitializer` if config says so, then returns `new JdbcRecoveryStore(dataSource, config.snapshotTtlSeconds())`.

#### `V1__create_dr_tables.sql`

Flyway-compatible migration script matching `SchemaInitializer` DDL. For production environments with restricted DB permissions.

### forage-dr-engine

#### `ShutdownPersistenceRoutePolicy`

Extends `RoutePolicySupport`. Tracks in-flight exchanges via `ConcurrentHashMap<String, Exchange>`.

- `onExchangeBegin` — adds exchange to map
- `onExchangeDone` — removes exchange from map
- `onStop` — drains remaining exchanges to `RecoveryStore` as SHUTDOWN snapshots

Each save wrapped in try/catch so one failure doesn't block others. No SIGTERM hooks needed — Camel lifecycle calls `onStop()` on shutdown.

#### `ShutdownPersistenceRoutePolicyFactory`

Implements `RoutePolicyFactory`. Creates one `ShutdownPersistenceRoutePolicy` per route. Registered on the CamelContext by `DisasterRecoveryBeanFactory`.

#### `CheckpointProcessor`

Extends `DelegateAsyncProcessor` to preserve Camel's async engine. Saves a CHECKPOINT snapshot before delegating to the wrapped processor.

Checkpoint failure does not break processing — caught, logged as warning, processing continues.

#### `CheckpointInterceptStrategy`

Implements `InterceptStrategy`. Wraps every processor with a `CheckpointProcessor`. Registered on the CamelContext by `DisasterRecoveryBeanFactory`.

#### `RecoveryReplayService`

Replays persisted exchanges on startup. Called after CamelContext has fully started.

1. Collects all active route IDs
2. Loads shutdown exchanges first (higher priority)
3. Loads checkpoints per route
4. Replays via `ProducerTemplate.send()` to the route's endpoint URI
5. Skips snapshots for routes that no longer exist
6. `ProducerTemplate` properly closed via try-with-resources

**Important:** Phase 1 replay is from route start. Checkpoints track progress per-processor, but initial replay re-injects from the route consumer. Mid-route resume is a future enhancement.

#### `AiStateRecoveryAdvisor` (utility)

Scans the Camel registry for in-memory AI provider class names (`MessageWindowChatMemoryBeanProvider`, `MessageWindowChatMemory`) and logs warnings suggesting persistent alternatives (Redis, Infinispan).

#### `RecoveryEventNotifier`

Extends `EventNotifierSupport`. Logging-only stub for future observability:
- `ExchangeCompletedEvent` → TRACE
- `ExchangeFailedEvent` → DEBUG

Future versions may emit metrics/traces via Micrometer or OpenTelemetry.

#### `DisasterRecoveryBeanFactory`

The orchestrator. Implements `BeanFactory`, discovered via ServiceLoader.

**Initialization sequence** (deferred to `CamelContextStartedEvent`):

1. Check `config.enabled()` — bail if false
2. Discover `RecoveryStoreProvider` via ServiceLoader
3. Wire `DataSource` from Camel registry (for JDBC providers)
4. Register `ShutdownPersistenceRoutePolicyFactory` (if `shutdownPersistence()`)
5. Register `CheckpointInterceptStrategy` (if `checkpointEnabled()`)
6. Run `RecoveryReplayService` (if `replayOnStartup()`)
7. Run `AiStateRecoveryAdvisor` (if `aiStateCheckEnabled()`)
8. Register `RecoveryEventNotifier`

Each feature is individually toggleable via config switches.

## Runtime Flow

### On Startup

```
CamelContext starts
  └─ DisasterRecoveryBeanFactory.configure() registers event listener
     └─ CamelContextStartedEvent fires
        └─ initializeOnContextStarted()
           ├─ Discover RecoveryStoreProvider (ServiceLoader)
           ├─ Lookup DataSource from registry
           ├─ Create RecoveryStore
           ├─ Register ShutdownPersistenceRoutePolicyFactory
           ├─ Register CheckpointInterceptStrategy
           ├─ Replay persisted exchanges (shutdown + checkpoints)
           ├─ Advise on in-memory AI providers
           └─ Register RecoveryEventNotifier
```

### During Route Processing

```
Exchange enters route
  └─ ShutdownPersistenceRoutePolicy.onExchangeBegin() tracks it
     └─ Each processor wrapped by CheckpointProcessor
        └─ Snapshot saved before delegation
           └─ Processing continues
              └─ ShutdownPersistenceRoutePolicy.onExchangeDone() untrack
```

### On Shutdown (SIGTERM)

```
SIGTERM received
  └─ Camel begins graceful shutdown
     └─ ShutdownPersistenceRoutePolicy.onStop() for each route
        └─ Drain in-flight exchanges to RecoveryStore
           └─ Each exchange serialized as SHUTDOWN snapshot
```

### On Restart (Recovery)

```
New pod starts → CamelContext starts
  └─ RecoveryReplayService.replay()
     ├─ Load shutdown exchanges → replay via ProducerTemplate
     └─ Load checkpoints per route → replay via ProducerTemplate
        └─ TTL-expired snapshots purged during load
```

## Challenges and Limitations

- **Async processor wrapping** — `CheckpointProcessor` extends `DelegateAsyncProcessor` to not break Camel's async engine
- **Thread safety** — in-flight exchange tracking uses `ConcurrentHashMap`
- **Non-serializable data** — skipped with warnings, snapshot marked as partial
- **At-least-once** — replayed exchanges re-execute external calls (including LLM calls); users should use `IdempotentConsumer` for dedup
- **Mid-route resume** — not yet implemented; replay re-injects from route start
- **Engine-to-JDBC coupling** — `DisasterRecoveryBeanFactory` has `instanceof JdbcRecoveryStoreProvider` check; accepted for now, decouple when adding Redis/Infinispan backends
